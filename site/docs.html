Getting started

Install the CLI with Bun 1.3.14 or newer available, then choose where requests run. Hosted Jev is opt-in. Local Qwen models and the review and verify commands are experimental.

Install the release

The GitHub release installs the CLI on macOS, Linux, or Windows. --allow-scripts=node-llama-cpp permits the native inference package’s install script. Installation does not download model weights.

Choose hosted Jev

Get a key from TypeSafe and provide TYPESAFE_API_KEY privately in your environment. Enabling Jev selects hosted-only routing. Sys1 saves the activation flag; the key stays in the environment.

# After setting TYPESAFE_API_KEY privately:
sys1 jev enable
sys1 jev status

Or choose a local model

Setup downloads Qwen3 1.7B. Start the local daemon for application requests or review commands using --gateway. Evaluate this experimental model on your own cases before relying on its answers.

sys1 setup --tier quality
sys1 up
sys1 status

Preview the download with sys1 setup --dry-run --json. sys1 doctor reports the runtime, model store, routing, and daemon state. For a client-only install or a source build, see the README.

Jev and System One models

System One models evaluate supplied state and answer questions in a format you define. Jev is TypeSafe’s hosted model. Sys1 connects this decision API to agent workflows and application code, and can route the same request format to other configured backends.

Applications can use Sys1’s open-source, Jev-compatible HTTP gateway on 127.0.0.1, or call it through the Node and Bun client. Both use POST /v1/systemone.

Noul: yes or no
Ask whether a condition holds. The noul field gives the probability of yes, from zero to one.
Choice: named alternatives
Define the allowed answers. Receive the chosen name, the probability of each option, and confidence.
Score: an ordered scale
Define ordered criteria. Receive a probability-weighted score on a zero-based scale, the labels, probabilities, and confidence.

Use these answers to prioritize investigation, classify evidence, or choose a workflow in code. Sys1 validates the response against the request. Your application still decides which actions are allowed and checks whether the model works on representative examples.

Make your first Jev request

After enabling Jev above, run sys1 up to start the loopback gateway. Save this request as request.json:

request.jsonIllustrative input
{
  "model": "typesafe/jev-1.13.0",
  "state": { "result": "The check exited with code 1." },
  "questions": {
    "failed": {
      "type": "noul",
      "instructions": "Does the supplied result report a failed check?"
    }
  }
}
Send the request
sys1 eval --file request.json --json

Read answers.failed.noul as the model’s probability of yes. The example demonstrates the API; use the exit status directly when your code already has it. Review and verify can call Jev without a daemon. The client, sys1 eval, and commands using --gateway need one.

Choose the model and handle failures

The request pins typesafe/jev-1.13.0. A TypeSafe alias such as jev-latest can change; keep a versioned model ID when comparing runs or setting thresholds. Enabling Jev keeps requests on hosted-only routing, so a provider failure returns an error without substituting Qwen. HTTP errors do not trigger a retry.

For a missing credential or unavailable gateway, inspect sys1 jev status and sys1 doctor. Restart the daemon after changing its environment. A backend_response_invalid error means Sys1 rejected the returned answer format; keep the error in your evaluation results.

Jev currently accepts text, including structured text in JSON. TypeSafe documents its model versions, prices, and changing rate limits. A probability is not a guarantee that an individual answer is right; local models using the same format do not inherit Jev’s calibration.

Review changes with your agent

The sys1-review project skill guides an agent through selecting a batch of Git changes, applying reusable rules, investigating candidates, and recording feedback. Its instructions work with Codex, Claude Code, and Devin; other agents can call the CLI directly.

The bundled rules check newly empty catch blocks and removed test assertions in JavaScript and TypeScript. Add and evaluate repository rules for other conventions or languages.

sys1 review setup codex --dry-run --json
sys1 review setup codex
sys1 review checkpoint --staged --model typesafe/jev-1.13.0 \
  --max-requests 10 --dry-run --json -- src test

Run setup inside your repository. Use setup claude-code or setup devin for those agents. Setup installs a skill file and no automatic hooks. In the checkpoint preview, inspect selected files, rules, skipped evidence, and request count. With Jev enabled and the source ready to send, repeat without --dry-run.

Use --worktree for current files or --since <ref> for committed changes. Paths after -- keep the selection within your task. Find active rules with sys1 rules list; repeat --rule <id> to choose checks. Repository-specific rule packs can cover conventions in your own code and guides.

sys1 review issues --json
sys1 review feedback <finding-id> useful --json

Investigate each candidate in the code before marking it useful, incorrect, or unverifiable. Findings are advisory, and scores are not calibrated defect probabilities. Keep your normal tests and review.

Complete unchanged batches can reuse their review for up to 24 hours. Local metadata preserves feedback without storing source or model answers. Recheck evaluates available original evidence; changed or missing evidence does not establish a fix. A new checkpoint and relevant tests check the repaired batch.

Verify completion claims

The sys1-verify project skill guides an agent through checking a completion message. Its sys1 verify command compares that message with reachable evidence. It can identify unpushed commits, uncommitted files, unmerged linked pull requests, or a fetched page that lacks the claimed change.

sys1 verify setup codex --dry-run --json
sys1 verify setup codex
sys1 verify --message /tmp/final-message.txt \
  --model typesafe/jev-1.13.0 --dry-run --json

Use setup claude-code or setup devin for those agents. The skill can be installed alongside sys1-review or on its own. Save the message outside your Git worktree, for example at /tmp/final-message.txt on macOS or Linux, then run the preview inside the repository. On Windows, choose an equivalent external path. It reads local Git state and makes no model calls or page fetches. Inspect the plan and repeat without --dry-run; message text and any fetched page text go to the selected backend.

Without --message, Sys1 finds the newest matching local Devin session and reads its final message and recent check-command results. Codex, Claude Code, and other agents supply a file or pipe text with --message -. Automatic test-result evidence currently comes from Devin transcripts only.

Exit 7 means a claim contradicts reachable evidence; exit 8 means the run was incomplete. Missing or unreachable evidence is unverifiable. Exit 0 means no contradiction was found, including when evidence is unavailable; it does not prove completion or deployment correctness.

Integration modes

Use the same request and answer format from application code. Choose whether your app calls a server, runs the router itself, or connects to a local daemon.

Portable client

Use the dependency-light @hraness/sys1/client entry from Node 24 or Bun. It validates requests, bounds response bodies, propagates cancellation, and makes one explicit HTTP attempt.

npm install --omit=optional \
  https://github.com/hraness/sys1/releases/download/v0.17.0/hraness-sys1-0.17.0.tgz

Run sys1 up for a local daemon. The endpoint is POST /v1/systemone; discovery is GET /v1/models; liveness is GET /healthz.

Backends & models

Every backend accepts the same request and returns the same answer format. That says nothing about how well it answers, so keep the model identity and routing policy visible in your app.

Hosted Jev 1.13.0
TypeSafe’s hosted System One decision model. Sys1 sends requests to its POST /v1/systemone API. Enabling Jev selects hosted-only; the credential remains environment-only. Network-inclusive timing and provider capacity are outside local measurements.
Local Qwen3 1.7B
Selected by the quality setup tier and run through the pinned llama.cpp adapter. Local probability readout is experimental and must be evaluated on your own representative cases.
Local Qwen3 0.6B
Explicit compact diagnostic tier. It is not a memory-driven fallback and cannot silently replace the configured local model.
Local Qwen3.5 4B
Larger experimental model, a 2.55 GiB download. Install it with sys1 pull qwen3.5-4b; it answers only when you select it.
Compatible HTTP service
Register a service that implements POST /v1/systemone and GET /v1/models. Select it explicitly; adding a backend does not alter default routing.
Kev
Kev is a set of trainable decision models that runs as your own server. Register it with --adapter kev. Sys1 handles its required fields, two-decimal probability output, and structured score labels. You own the checkpoint, server, and any training.

Sys1 adapters return validated Jev-compatible answer shapes. They do not make generic local weights interchangeable with Jev, OpenJev, or another provider's calibration. For background on TypeSafe and Jev, see the Hraness TypeSafe dossier.

Profiles and evaluation

Give each task a versioned set of questions and a model route. Reuse the same profile from application code or the CLI; each call supplies only the changing state.

const triage = createProfile({
  version: 1, id: "triage", revision: "1",
  model: "kev/kev-latest",
  questions: {
    urgent: { type: "noul", instructions: "Is there an active outage?" }
  }
});
const result = await client.evaluate(triage.request(ticket));

Import createProfile from @hraness/sys1/client. Save the definition as JSON for sys1 eval --profile triage.json, with {"state": ...} on stdin. Profiles also work with Jev and built-in local model routes.

Start by improving instructions and criteria against fixed application examples. If fine-tuning helps, train Kev separately, calibrate and evaluate the checkpoint, then publish a new profile revision pointing at its server. Profiles do not collect training data or start training jobs.

From a source checkout with Bun and project dependencies, evaluate a profile on labeled examples. The included experiments cover failure triage, excerpt relevance, and claim support. They are separate from the installed project skills.
