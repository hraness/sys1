# Jev workflow screening: September 28, 2026

This small synthetic trial tested three experimental Sys1 profiles: failure
triage, evidence relevance, and claim support. Jev 1.13.0 returned valid answers
matching the labels for 45 of 48 submitted cases. Three relevance cases returned
errors. Each case was submitted once; none was retried.

The most useful next candidate is **claim support**, which matched all 16 labels.
Its comparator is deliberately weak, so this is a reason to test larger,
representative examples. Production use requires evidence on those tasks. Triage showed no advantage over simple error matching. Relevance
needs a response-format investigation before a broader pilot.

These are **source-checkout experiments**, not additional installable skills.
See the [evaluator guide](../../../docs/profile-evaluation.md),
[profiles](../../../examples/workflows), and
[frozen fixture manifest](../manifest.json).

## Results

“Correct” means matching the authored fixture label using the frozen grading
rule. Errors stay in the denominator; they are not counted as wrong labels or
silently discarded.

| Profile and split | Correct / submitted | Errors | Baseline correct / all cases | Baseline correct / cases Jev completed |
| --- | ---: | ---: | ---: | ---: |
| Failure triage · development | 8/8 | 0 | 8/8 | 8/8 |
| Failure triage · screening | 8/8 | 0 | 8/8 | 8/8 |
| Evidence relevance · development | 6/8 | 2 | 6/8 | 5/6 |
| Evidence relevance · screening | 7/8 | 1 | 0/8 | 0/7 |
| Claim support · development | 8/8 | 0 | 3/8 | 3/8 |
| Claim support · screening | 8/8 | 0 | 3/8 | 3/8 |

The development and screening examples were authored separately and frozen before
the run. Both sets are synthetic and public; “screening” does not mean a private
holdout or independently certified benchmark.

- **Triage:** Jev and signature matching both got 16/16. These examples do not
  justify adding model calls to ordinary error matching.
- **Relevance:** Jev got 13/13 among valid answers, while token overlap got 5/13 on
  those same cases. Across all submissions, Jev delivered 13 correct answers and
  three errors; the baseline got 6/16. The semantic result is promising, but the
  errors are an operational limitation.
- **Claim support:** Jev got 16/16. The literal-match baseline predicted
  `insufficient_evidence` on all 16 examples and got 6/16. It looks for the full
  normalized claim or a simple negation; none matched in these examples. This is
  a weak comparator, not a competing entailment model or an optimized rules
  system. The profile judges support within the supplied evidence, not truth
  beyond it.

## Errors and the interrupted first run

The [initial report](2026-09-28-initial.md) is preserved. Its run stopped after
18 provider submissions: 17 valid answers and one gateway HTTP 502. The following
case aborted locally before any provider submission.

A separate continuation submitted only the 30 cases the provider had never
received. It preserved the original prompts, labels, baselines, ordering, and
grading. The original failed request was excluded. The combined accounting uses
each case's one provider submission; the original local abort remains visible in
the initial report.

| Case | Split | Observation |
| --- | --- | --- |
| `lexical-near-miss` | Development | Initial run: gateway HTTP 502. The original harness did not retain the provider status or rejection type, so its cause remains unknown. |
| `direct-answer-with-quoted-instruction` | Development | Continuation: provider HTTP 200, followed by gateway HTTP 502 with `backend_response_invalid`. |
| `relevance-screen-join-different-domain` | Screening | Continuation: provider HTTP 200, followed by gateway HTTP 502 with `backend_response_invalid`. |

All three belong to evidence relevance. The two observed continuation errors
establish response-contract rejection, not the specific invalid field or the
correctness of the rejected answer. Request and response bodies were not retained
in the diagnostic records. The first error cannot be assigned the same cause
from this evidence.

The continuation added sanitized error metadata and continued to the next unused
case after an ordinary HTTP or response-validation failure. Authorization errors,
transport ambiguity, model mismatch, and exhausted limits remained stop
conditions. It did not change the evaluator, gateway validation, profiles, or
fixtures. This orchestration change is a limitation of comparing the two runs.

## Timing and execution

The configured model was `typesafe/jev-1.13.0`; valid responses identified
`jev-1.13.0`. Execution used hosted-only routing through the owned Sys1 loopback
gateway, with local inference disabled, concurrency one, and zero retries.
The initial and continuation reports record 18 + 30 model POSTs and 36 + 60
provider-discovery GETs, with no blocked network calls. There are no unsubmitted
cases left in this trial.

Across the 45 valid responses, the median elapsed time was **350.4 ms** and the
nearest-rank p95 was **426.0 ms**. Across all 48 submissions, including errors,
the median was **354.8 ms** and p95 was **426.0 ms**. These are one observation per
case, not a repeated latency benchmark.

Timing includes the evaluator's HTTP call, the local gateway, provider discovery,
hosted inference, and response validation. It excludes deployment, process
startup, fixture preparation, and baseline computation. Vercel region was not
reported. Provider hardware, cache behavior, and isolated model speed are unknown.
Do not compare these numbers directly with the differently timed historical
[Sys1 evaluation studies](https://sys1.io/docs/evaluations).

The valid responses reported **28,898 input tokens and 2,337 output tokens**.
Usage for the three rejected responses is unavailable, so this is not total
billable usage and no monetary cost is claimed.

## What this supports

The trial shows that the source evaluator can expose coverage, matched labels,
baseline results, and response errors for reusable profiles. It supports a larger
claim-support trial and diagnosis of relevance response validity. It does not
establish production accuracy, probability calibration, robustness to arbitrary
instructions embedded in evidence, performance on real repositories, or a benefit
over stronger task-specific systems.

No prompts, fixtures, baselines, or thresholds were tuned after seeing the
results. A future improvement should receive a new report and fresh screening
examples while keeping these observations intact.
